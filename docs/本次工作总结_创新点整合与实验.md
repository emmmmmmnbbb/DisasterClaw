# DisasterClaw 本轮工作总结（创新点整合 + 实验验证）

> 这份文档用尽量简单的语言，说明这一轮我们做了什么、为什么这么做、结果如何。不涉及具体代码写法，只讲思路和结论。

---

## 1. 这一轮要解决的问题

在开始动手之前，我们先讨论清楚了一件事：DisasterClaw 之前同时强调好几个模块（分层规划 HSPM、文字地图 STMR、记忆图、复核机制……），容易让人觉得是"堆功能"而不是"有一个清晰的科研贡献"。

讨论后确定了新的定位：

- **真正的核心创新**只有一个——**"不确定性驱动的主动复核"**（UAV 发现灾情判断不太确定时，自己决定要不要飞低一点/换个角度再看一眼，而不是瞎猜）。
- 其余部分（俯视 VLN 问题定义、分层规划、语义地图记忆）都降级为"支撑这个核心创新的配套模块"，不再和核心创新平分秋色。
- 同时借鉴了两篇论文的思路：一篇讲"利用双时相（灾前+灾后）影像做变化检测"，另一篇讲"怎么把无人机智能体的任务和评测体系定义得更规范"。这两点被用来**充实"不确定性"这一件事到底怎么算得更靠谱**，而不是新增独立的贡献点。

所以这一轮所有的代码改动，本质上都是围绕"让不确定性这件事更严谨、更能被验证"展开的。

## 2. 具体做了哪些改动（按模块说明，不讲代码细节）

### 2.1 文档

把上面讨论出的新定位、新增的两个阶段（P5 校准感知、P6 评测严谨性补丁）以及后续要做的实验清单，整理写进了项目的实施计划文档里，方便以后回顾。

### 2.2 数据集处理

- 之前用来训练建筑损伤检测器的数据集切分方式有问题：本该"完全没见过"的灾害类型，其实混进了训练集里，导致"跨灾害泛化能力"这个说法站不住脚。这一轮修复了切分逻辑，专门留出几种灾害类型作为"真正没训练过"的测试集。
- 新增了一套"灾前+灾后"配对数据的处理流程，为的是让模型不只看灾后一张图片猜损伤程度，而是能对比灾前灾后的变化来判断——这更符合真实救灾场景的逻辑（一栋本来就破旧的房子，和一栋刚被摧毁的房子，光看灾后图很难区分，但对比灾前灾后就清楚了）。



### 2.3 新增"变化感知"模型

新增了一个小模型，输入灾前+灾后两张图，同时输出：这块区域有没有发生变化、损伤等级是什么、以及对这个判断有多大把握（概率，不是简单的"是/否"）。

这里特别做了"温度校准"处理——通俗理解就是：模型自己说的"把握程度"往往是不准的（比如说"90%确定"，但实际统计下来只对了70%），温度校准就是用一个简单的数学方法，把模型说的"把握程度"校正得更接近真实情况。这一步对我们后面"要不要复核"的判断非常关键，因为如果模型的自信程度本身就不可信，那"发现不确定就复核"这套逻辑也无从谈起。

### 2.4 新增校准效果评测工具

写了一个专门的评测脚本，用来检验上面说的"校准"到底有没有起作用——用几个统计学里公认的指标（数值越小越好），对比"校准前"和"校准后"模型自信程度的可信度。

### 2.5 让感知模块能"说出"自己的把握程度

原来的感知模块（负责识别建筑、道路等）只会给出一个最终判断结果，这次改造后它可以额外暴露出"每个类别的可能性分布"，供后面的复核逻辑使用。

### 2.6 升级"要不要复核"的判断逻辑

这是核心改动。原来判断"要不要飞低一点复核"用的是一套人工设定的经验规则（查表）。这次新增了两种更严谨的判断方式：

- 用上面说的"校准后的把握程度"来算不确定性（数学上叫"熵"，简单理解就是"模型有多纠结"）。
- 更进一步，还能预测"如果我真的飞低复核一下，纠结程度大概能降低多少"，只有当预计能降低足够多的时候才会去复核，而不是看到风吹草动就飞过去，避免瞎折腾。

同时为了做对比实验，还补充了两个"陪跑"策略：完全不复核、随机复核，方便和正式的策略比较到底哪个更划算。

### 2.7 让无人机的"选方向"更聪明一点

在没有明确目标的情况下，无人机原来选择往哪个方向飞主要靠大语言模型"自由拍板"。这次新增了一个可选开关，把"大模型打分 + 已知方位线索 + 优先探索没去过的区域"三种信号综合起来打分再选择，理论上应该能减少绕远路的情况。这个改动定位成"工程改进"，不算主线创新。

### 2.8 补充自动化测试

针对上面新增的判断逻辑，补充了自动化测试用例，确认新逻辑在各种情况下表现符合预期，也没有破坏原有功能（改动后所有测试全部通过）。

## 3. 跑了哪些实验，结果怎样（这是最重要的部分，如实汇报，包括不如预期的结果）

我们一共设计了四组实验，编号 E10~E13。这里说明白：**跑实验不是为了证明"我们的方法很厉害"，是为了搞清楚"到底哪个部分真的有用、哪个部分没用"**，所以下面既有符合预期的结果，也有不符合预期、甚至发现新问题的结果，都如实记录了。

### E11：六种"要不要复核"的策略里，哪个最好？

**结论：目前样本量太小，看不出明显差别；但意外发现了一个统计口径上的漏洞。**

我们比较了六种策略（不复核、随机复核、固定复核、原来的经验规则、新的校准不确定性、加了"预测收益"的更聪明版本），本来预期"越聪明的策略效果应该越好"。但因为这次每种策略只测了40个任务（样本较少），结果发现六种策略在最终成功率上的差异在统计上都不算显著——换句话说，现在还不能说"哪种复核策略明显更好"，需要以后测更多样本才能看清楚。

比较有价值的一个发现是：我们原本设计的一个关键指标——"每次复核到底帮忙降低了多少不确定性"——在这次六种策略里全部显示为 0。深入检查后发现，这**不是复核真的没起作用，而是这个指标的统计方式有问题**：现在的统计只有等无人机"彻底确认/彻底否定"某个判断之后才会记一笔账，但很多任务在无人机还没走完这个"确认流程"之前就已经结束了（到达终点或者步数用完），导致这笔账一直没被记上，看起来就像是"复核完全没用"。这是一个明确找出来的、需要后续修复的问题，已经记录在文档里，不是这次能顺手改完的小问题。

**结果文件在哪里：**

- 不复核 / 随机复核 / 固定复核 / 现有经验规则 四档：`runs/benchmarks/20260711_185109_e11a/`（成绩单 `summary.md`、六档合并对比表 `report.md`、机器可读数据 `results.json`、每题明细 `episodes.jsonl`）
- 校准不确定性 / 加信息增益预测收益 两档：`runs/benchmarks/20260711_194030_e11b/`（`summary.md`、`results.json`、`episodes.jsonl`）



### E12：把"选方向"改聪明一点，真的能少绕路吗？

**结论：目前没看出稳定的好处，效果好坏不一，之前把它定位成"次要改进而不是主要贡献"是对的判断。**

本来的猜测是：这个改进应该能让无人机在"目标不明确、需要多绕几个地标才能找到"的困难任务上少走弯路。但实测下来，困难任务上几乎没有变化，反而是中等难度的任务上有点提升；不同灾害类型之间效果也不统一。所以这次没能证实最初的猜测，如实记录下来，继续保持"这是辅助改进，不是核心创新"的定位是稳妥的。

**结果文件在哪里：** `runs/benchmarks/20260711_185120_e12/`（成绩单 `summary.md`、含难度分桶+跨灾种拆解+显著性检验的完整报告 `report.md`、机器可读数据 `results.json`、每题明细 `episodes.jsonl`）

### E13：换更多、更难的场景测试，结论还稳不稳？

**结论：基本稳，但也发现了一个"测试集没做干净"的历史遗留问题。**

- 建筑损伤检测器在"完全没训练过的灾害类型"上的表现，本来预期应该比"训练时见过的类型"差一些（这才符合常理）。但实测下来没有变差，反而还好了一点。深入检查发现，这是因为检测器**训练的时候用的数据集切分，并没有真正把这些"没见过的灾害类型"排除在训练集之外**（这个问题在之前的数据处理环节已经修复了切分逻辑，但训练检测器用的是修复前的旧版本），所以这次的"跨灾害测试"其实只是验证了新的数据切分流程本身没问题，还不是一次严格意义上的泛化测试。要做严格测试，需要用新切分好的数据重新训练一遍检测器，这一步还没做，留作后续工作，已经如实写进文档，没有隐瞒。
**结果文件在哪里：** `runs/benchmarks/e13/yolo_detector_generalization.json`（同源测试集 vs 跨灾害留出集的完整数据对比，含说明文字）；对应的混淆矩阵/PR 曲线等图表在 `runs/detect/val3/`、`runs/detect/val4/` 下。
- 把测试任务从40个扩大到了更多、更多样的灾害场景后重新跑了一遍主要对比实验，结论方向和之前一致：几个规划/复核/记忆相关的模块，都没能稳定提升最终的任务成功率。这进一步印证了这次"把核心创新收窄到只讲复核机制这一件事"的判断是合理的，其他模块更适合当作"配套系统"而不是"拿去证明有效"的主要论点。
**结果文件在哪里：** `runs/benchmarks/20260711_185454_e13scale/`（成绩单 `summary.md`、含显著性检验的完整报告 `report.md`、机器可读数据 `results.json`、每题明细 `episodes.jsonl`）；扩大后的题库文件：`backend/data/benchmarks/vln_testset_v2_240.json`。

## 4. 过程中遇到的意外情况

- GPU 是和别人共用的服务器资源，中途显存被别人的任务抢占过，导致一次模型训练在快训练完的时候被意外打断、白跑了一遍。后来给训练流程加了"每一轮训练都自动存一次进度"的保险措施，重跑之后就顺利训练完成了，以后再遇到类似情况也不会全部损失。
- 因为GPU资源时松时紧，这次实验是抓住了几个空闲窗口、分批在不同显卡上同时跑完的，所以实际完成顺序和最初设想的先后顺序略有出入，但四组实验最终都跑完了。
